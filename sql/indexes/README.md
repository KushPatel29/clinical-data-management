# Indexes

Every index in this warehouse, and the reason it exists.

An index with no recorded rationale is an index nobody will dare drop, and an
unused index is not free: it is written on every insert, and inserts are where
this warehouse spends most of its time. So each one is listed here with the
access path it serves.

## Written by the measurement script

The two files in this directory are generated by
[`analytics/measure_performance.py`](../../analytics/measure_performance.py)
alongside the before-and-after numbers in
[`docs/performance.md`](../../docs/performance.md). They are the only two
indexes in the repository whose effect has been measured rather than reasoned
about.

| File | Index | Serves |
|---|---|---|
| `IX_FactObservation_code_date.sql` | covering nonclustered | Q1 — one observation code over a date range, the shape behind every "is this measure drifting" dashboard tile. |
| `NCCI_FactObservation.sql` | nonclustered columnstore | Q2 — a whole-fact-table aggregate across every code and quarter, the shape of a Power BI import refresh. |

Neither is created by `db/migrate.py`. They are applied by the measurement run
and can be dropped with `python analytics/measure_performance.py --revert`,
because an index whose justification is a benchmark should be visible as such
rather than buried in the schema.

**Q3 has no file here, and that is the point.** The third measured query was
fixed by a rewrite rather than an index — replacing a scalar UDF with an inline
table-valued function so the shredding statements stop being ineligible for
parallelism. It is by a wide margin the largest effect measured, and no index
would have helped: the plan was serial, not short of a seek. Reaching for an
index first is the reflex worth resisting.

## Declared in the schema files

The rest are created with the tables they belong to, because they are structural
rather than tuning — dropping one breaks a load rather than slowing a report.

### `sql/01_raw.sql`

| Index | Reason |
|---|---|
| `PK_fhir_resource` (clustered, `resource_type, resource_id, version_id`) | The idempotency contract. Also makes every "resources of type X" filter a seek. |
| `IX_fhir_resource_type_updated` | The incremental access path: what changed, by type, since when. |
| `IX_fhir_resource_current` (`resource_type, resource_id, last_updated DESC`) | Covers the version-ranking that `raw.usp_refresh_current_version` performs. Holds no payload, so ranking 1.6 million resources never touches the JSON. |
| `PK_current_version` (clustered) | Every shredding statement joins through it. |

### `sql/04_norm.sql`

SQL Server indexes the primary key and nothing else. **An unindexed foreign key
is a table scan on every join and a lock escalation risk on every parent
delete** — and these are the joins the entire warehouse is built out of. One per
foreign key:

| Index | Reason |
|---|---|
| `IX_encounter_patient` | Patient timeline. Includes `period_start, class_code` so the common "encounters for this patient in this window" never leaves the index. |
| `IX_encounter_org`, `IX_encounter_performer` | Site and clinician rollups. |
| `IX_condition_patient` (+ `code_concept_id, onset_datetime`) | Comorbidity and cohort queries. |
| `IX_condition_encounter` | Diagnoses recorded on an encounter. |
| `IX_observation_patient` (+ `code_concept_id, effective_datetime`) | The largest table's most common access path. |
| `IX_observation_encounter` | Results attached to a visit. |
| `IX_procedure_patient`, `IX_procedure_encounter` | Same, for procedures. |
| `IX_medication_request_patient`, `IX_medication_request_encounter`, `IX_medication_request_requester` | Same, for orders, plus prescriber attribution. |
| `IX_resource_coding_concept` | "Which resources carry this code", the reverse lookup the terminology tables would otherwise scan for. |

### `sql/05_dw.sql`

| Index | Reason |
|---|---|
| `UQ_DimPatient_one_current` (filtered unique, `WHERE is_current = 1`) | **The SCD2 guard.** One current row per patient, enforced by the engine. A check constraint cannot express it because the rule is about a *set* of rows. This is what turns the classic two-current-rows bug — every measure silently doubled — from something you find in a report into something the insert refuses. |
| `IX_DimPatient_lookup` (`patient_id, effective_from, effective_to`) | The Type 2 range join every fact load performs. |
| `UQ_*_natural` on each fact | The natural key. Makes the load's `MERGE` a seek and makes a duplicate impossible rather than merely detectable. |
| `UQ_DimDate_full_date` | Date-key lookups join on `full_date`, not on `date_key`, so the fact loads degrade an out-of-range date to Unknown instead of failing a foreign key. |

## What is deliberately not indexed

- **`raw.fhir_resource.payload`.** No full-text index, no JSON index, no computed
  columns over `JSON_VALUE`. Everything that needs to query inside the JSON does
  it once, during the shred, into `norm`. Indexing the raw JSON would be
  building a second query surface on a layer whose job is to be an unaltered
  record of what arrived.
- **The `dw` dimensions' descriptive columns.** They are small enough that a
  scan is cheaper than a seek plus a lookup, and every one of them would be
  another write on every load.
